## 1. 为什么单独安排这个阶段

用户已手工跑通早期 NEMU、AM、NPC harness 和 RTL。当前需要恢复部分基础知识、补齐跨层知识结构，并理解 AI 辅助引入的增量。目标是掌握设计与验证的关键逻辑，能够对项目中的技术陈述负责。

2026-10-25 已确认：四篇 M5 S3 知识补充文档已提交并打印，入口为 [knowledge-notes](../knowledge-notes/README.md)。这是学习材料准备完成，**不代表已经读完或考察通过**。阅读和提问可以与后续实现并行；集中复盘安排在本轮实现冻结后。

本轮顺序为：

```text
M5 按既定范围验收
  → GShare 限定增量：功能回归 + 同条件性能/面积/时序对照
  → 冻结可复现版本
  → 本阶段：理解考察、补缺、简历 v1
  → 投递与回顾并行
```

这里的“实现完成”指本轮明确的 M5 + GShare 范围，不要求完成 roadmap 中所有长期扩展。I-cache、SDRAM、更多外设及更深流水线不自动加入本轮。

## 2. “理解精髓”的可观察标准

面向第一份 Design Engineering / Design Verification 实习，优先检查下面这些能力。标准用于本项目复盘，不宣称是所有公司的统一要求。

| 能力 | 应能做出的行为 | 本工程中的考察例子 |
| --- | --- | --- |
| 讲清整体结构 | 不看答案画出主要模块、接口和数据流，区分宿主机与目标 CPU、功能 RTL 与仿真观察逻辑 | 一条指令从取指到提交；BIN、EXE、REF 分别由谁执行 |
| 解释设计选择 | 说清需求、约束、当前方案及至少一种替代方案的代价 | 为什么单 outstanding；为什么锁存仲裁 owner；为什么先选 PSRAM |
| 推导时序与边界 | 针对具体事件顺序预测状态变化，能处理反压、flush、reset、异常等适用边界 | 请求已接受后发生 redirect；中断到来时有未完成访存 |
| 设计有效的验证 | 从需求提出输入、观察点、独立预期与失败条件，说明现有测试的检测边界 | DUT/REF 一致仍遗漏启动初始化；检查器怎样用负例验证 |
| 定位真实问题 | 从首个错误现象提出假设，选择证据验证，解释根因、修复与防回归 | 从提交记录、总线波形或 STA 报告追踪一个实际 bug |
| 解读定量结论 | 解释指标、测量范围与比较条件，区分已测、估计、未验证 | GShare 准确率与 cycles 的关系；200 MHz 约束点与 Fmax 的区别 |
| 完成小范围迁移 | 在理解后独立修改一个局部条件或新增测试，并选取适当验证 | 增加一个 AXI 反压场景；检查预测表索引别名；修改并验证一个局部控制条件 |

背出 API 名称、记住全部路径、重写全部基础设施不作为通过条件。关键源码可以查阅；看懂模型给出的解释与能独立推导，需要分别记录。

DE 重点落在数据/控制通路、状态机、时序与架构取舍、综合影响；DV 重点落在验证计划、stimulus/checker/参考模型、断言与覆盖、首错定位。公共基础都要能解释，深入练习优先选择与目标岗位和简历重点相符的主题。SV/UVM 等尚未掌握的岗位知识单独列缺口，不把现有 Python/C++ 验证经验直接等同于它们。

## 3. 学习可以使用 AI，考察要能区分独立完成与提示后完成

对一个主题按实际表现记录以下层次，不用一个总分掩盖具体缺口：

| 层次 | 观察依据 |
| --- | --- |
| 看懂讲解 | 能跟随材料，但暂时需要提示才能复述或定位 |
| 独立解释 | 无答案提示时能讲清因果和边界，回答针对实现的追问 |
| 对照证据 | 能打开正确版本的源码、测试、波形或报告，说明它们怎样支持结论 |
| 迁移应用 | 面对未背过的小变化，能推导行为、修改或补测试并验证 |

简历 v1 中重点陈述的主题应达到“独立解释 + 对照证据”；从中选择 2～3 个核心主题继续检查迁移能力。至少完成一次与岗位相关的小修改或新增测试练习。不要求仓库所有模块都达到相同深度，也不把全部通用题库作为开始投递的条件。

考察时先让本人回答，不先展示标准答案。若需要提示，记录提示内容；讲解补缺后换一个相邻场景复测，避免把刚听过答案的复述当作已经掌握。AI 评价也必须核对源码与实际结果，不能凭回答流畅或某个关键词出现就判通过。

个人贡献需要能分别说明：早期手工实现、后续 AI 辅助实现、上游复用、参考改造，以及自己做出的设计决策和验证。AI 辅助本身不免除对关键行为的理解，也不要求为了证明理解而逐行重写整个工程。

## 4. 实际怎样开展一轮复盘

冻结后先确定本轮源码版本和拟写进简历的 2～3 个主题，再开展一轮口述/证据检查和一次小练习。时间仅作练习建议，可按实际情况拆开进行。

1. **闭卷概述，约 10～15 分钟**：画架构和验证关系，说明实现范围、个人贡献、关键取舍；不使用 AI 提示。
2. **设计追问与证据定位，约 30～45 分钟**：选择一条执行路径或一次故障，先推导，再允许查源码、波形和报告核对。DE/DV 按目标侧重选择题目。
3. **小变化练习，另安排约 45～90 分钟**：在隔离分支或临时实验中修改局部行为或补一个有实际检测价值的测试。允许查手册/API，独立作出修改和验证选择；若使用 AI 提示，照实记录。
4. **集中补缺与相邻题复测**：只补这次暴露、且影响简历主题的缺口；需要长期保存的基础解释放入 `knowledge-notes`，阶段设计问答更新对应 `qa`。
5. **产出简历 v1**：每条技术表述能对应贡献、版本和证据；后续随投递继续补充理解和表达。

备选题要结合冻结版本生成。当前可以预留以下方向，但不能将尚未实现的中断或 GShare 当成已有成果：

- 对一条未完成取指安排 redirect，预测旧响应返回后哪些状态可以改变。
- 对 AXI 写事务改变 AW/W 顺序与反压位置，说明 owner 何时可以释放，以及测试怎样判断丢失或重复。
- 沿 data-copy 负例解释 CPU a0、仿真进程返回码和 Python 测试结论的联系。
- 中断实现后：在待响应 load/store 附近提出 IRQ，推导 EPC、提交顺序和副作用。
- GShare 实现后：解释预测时的索引与训练时的对应关系、历史更新策略，以及一次错误预测的恢复。
- 从一条真实 timing/DRV 报告找到对象，说明约束依据和修复的影响范围。

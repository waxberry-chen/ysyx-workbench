# GShare BPU 阶段 Q&A

> 2026-10-31；以下按已实现 RTL 与本地实验更新；服务器面积／时序对照仍待验。随有价值的进展更新，不要求每次提交补问答。

## Q1：没有 BTB，预测 taken 后的目标从哪里来？

取指响应返回后，predecode 从条件分支／JAL 编码提取立即数，用该指令的 PC 加偏移得到目标。GShare 只提供条件分支方向。当前 Fetch 单 outstanding，下一请求本来就要等响应，因此采用响应时预测；这并不证明 BTB 在所有实现里都没有收益。依据：[plan §1–2](../plan.md)。

## Q2：JAL 也需要 GShare 吗？JALR 为什么暂时不做？

JAL 是无条件直接跳转，目标由 PC 和指令立即数决定，前端可直接计算。JALR 的目标还依赖寄存器值，提前处理需要额外的数据依赖解决或目标预测。本轮让 JALR 保留现有 EXU 处理，以控制实现范围；JALR 指令和函数返回仍受支持。参考设计区分 x0、x1 和其他寄存器，配合读口与等待逻辑提前求目标，移植需要独立验证依赖、同拍写回和恢复。具体取舍与预计增量见 [plan 的 JALR 专节](../plan.md#jalr本轮保留-exu-处理前端提前处理暂缓)。JAL/JALR 都不进入初版条件分支 GHR/PHT 训练。

## Q3：为什么先用提交历史，而不照搬参考设计的推测历史？

只记录已提交的真实方向，错误路径不会污染 GHR，无需额外恢复快照；代价是前端历史可能落后于尚未执行的分支。参考设计已经有推测更新与恢复，本轮先验证更小的闭环，并用真实程序测量这种取舍的效果。预测时用到的 PHT index 仍要随指令保存，不能在训练时重新算。

## Q4：预测正确之后还需要 redirect 吗？

对于已正确预测的普通 branch/JAL，不应因为实际 taken 就再次清前端。EXU 核对实际下一 PC 与保存的预测下一 PC，发现不同才恢复；异常／IRQ／MRET 仍按原规则处理。预测方向错误但目标等于 PC+4 时，方向统计和是否需要恢复可能不同。依据：[恢复规则](../plan.md#23-metadata-与错误恢复)。

## Q5：怎样证明性能收益来自 GShare？

使用 OFF、JAL_ONLY、GSHARE 三模式：先看整体变化，再比较共同前端／JAL 处理下条件分支方向预测的增量。固定镜像、存储延迟、reset 和统计区间，分别报告方向准确率、恢复／错误取指及周期；同条件 DC/PT 给出面积与时序成本。固定六程序 OFF/GSHARE 为 1.114～1.201×；JAL_ONLY/GSHARE 为 1.001～1.198×。尤其 if-else 的总收益主要来自 JAL，不能全部归因于方向表。面积／时序还没有新结果，见 [实测与边界](../4-performance-ppa.md)。依据：[验收与比较口径](../test-plan.md)。

## Q6：初始参数与参考设计完全相同吗？

只有方向表的 128 × 2-bit 规模相同。参考采用 8-bit 推测历史并折叠，与 PC[7:1] 做 hash；本计划采用 7-bit 提交历史与 PC[8:2] 异或。参考的历史还包含 jump，本计划只记录条件分支。这个配置是简化实现的初始设计点，尚未通过实测证明最优。见 [本工程参数选择与依据](../plan.md#参数选择与依据)。

## Q7：预测器正确，为什么仍要把 index 放进 IFQ 和 opbuf？

预测时的 GHR 与提交时的 GHR 可能不同，提交时用 PC 再 hash 会训练另一项。预测 index 是这条指令当时做出的选择，属于必须随指令保存的上下文。counter 则不保存旧值：同项可能被其他分支训练过，必须在提交时对当前值饱和加减。单元测试同时覆盖了这两种情况。

## Q8：如何证明错误路径不会污染状态？

训练门控使用正常分支 commit；store/CSR 的架构副作用也由顺序提交／执行控制。定向程序先把一个 PHT 项训练为强 taken，循环退出后减到仍预测 taken 的状态，再让必不跳转的分支与其别名，把错误目标分别指向 store、CSR 写、非法指令、branch、取指错误位置；检查正确路径自检、DiffTest、异常数和恰好 43 次分支训练。仅看到程序退出正常不足以证明预测真的错过，测试还要求存在 predicted-T / actual-NT 事件。

## Q9：为什么条件分支准确率提高，程序加速却不一定明显？

条件分支只占部分动态指令；JALR、数据访存和正常取指延迟仍然存在。当前 Flash/PSRAM 通过真实串行控制器访问，取指和数据又共享总 outstanding 限额。因此要按同镜像比较 cycles，并用分开的 JAL_ONLY 模式解释贡献，不能把准确率直接换算为整机加速比。本轮没有新增 BTB/cache 来改变这个边界。

## Q10：能不能用 actual NPC != PC+4 当作真实 taken？

不能。合法条件分支可以跳到 PC+4，比较成立时方向仍是 taken，只是地址与顺序执行相同。此次训练直接使用 EXU 比较器的 `branch_taken`，恢复使用 actual/predicted NPC 比较；方向统计也单列。EXU 的 offset=4 定向确认这类分支无需错误恢复，不能让恢复判据代替方向训练。

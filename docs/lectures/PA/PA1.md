> 本笔记对应原讲义 `1.1.md` 至 `1.7.md`，面向快速推进实验。默认使用课程要求的 `riscv32` 主线；其他 ISA 的差异单独注明。原讲义仍是任务与验收要求的最终依据。

## 1. 实验目标

PA1 的核心不是立即实现完整 CPU，而是先建立理解和调试 NEMU 所需的基础设施：

- 从状态机视角理解计算机和程序运行。
- 读懂 NEMU 的启动、客户程序装载和执行主循环。
- 完成简易调试器 SDB 的基本命令。
- 实现表达式求值及随机测试工具。
- 实现监视点，为 PA2 之后的调试建立可靠工具链。
- 学会通过目录、关键词和上下文快速查阅 ISA 与工具手册。

最终应能解释并使用这条主线：

```text
main
  -> init_monitor
       -> parse_args / init_rand / init_log / init_mem
       -> init_isa: 装入内置客户程序并初始化寄存器、PC
       -> load_img: 可选地用镜像覆盖内置程序
       -> init_sdb
  -> engine_start
       -> sdb_mainloop
            -> cpu_exec
                 -> execute
                      -> exec_once: 取指、执行、更新 PC
```

## 3. 必备理论（对应 1.2）

### 3.1 TRM：最简单的计算机

TRM（Turing Machine，在本讲义语境中指最简单的真实计算机）至少包含：

- 存储器：保存程序和数据。
- PC：指出当前指令的位置。
- 寄存器：保存 CPU 正在处理的数据。
- 运算部件：执行加法等操作。

其工作方式可以压缩为：

```c
while (1) {
  从 PC 指示的存储器位置取出指令;
  执行指令;
  更新 PC;
}
```

**[必做] 从 CPU 视角手工执行求和程序**

```text
0: mov  r1, 0
1: mov  r2, 0
2: addi r2, r2, 1
3: add  r1, r1, r2
4: blt  r2, 100, 2
5: jmp  5
```

逐条更新 PC、`r1` 和 `r2`，理解它如何用简单指令计算 `1+2+...+100`；结束时 `r1=5050`，程序在 `PC=5` 自循环。这是建立“取指—执行—更新 PC”认识的必做内容，而不只是阅读示例。

NEMU 用 C 数据结构模拟这些部件：

- 物理内存：`nemu/src/memory/paddr.c` 中的 `pmem`。
- CPU 状态：`nemu/src/isa/$ISA/include/isa-def.h` 中的 `riscv32_CPU_state`，同时在 `nemu/include/isa.h` 中定义 `typedef concat(__GUEST_ISA__, _CPU_state) CPU_state;`, 全局实例 `cpu` 位于 `nemu/src/cpu/cpu-exec.c`。
- 指令执行循环：`cpu_exec()`、`execute()`、`exec_once()`。
- ISA 相关执行逻辑：`nemu/src/isa/$ISA/inst.c`。

### 3.2 计算机和程序都是状态机

计算机状态由所有时序部件的值组成，例如内存、PC 和寄存器。执行一条确定的指令，就是从当前状态转移到唯一的下一状态。

程序运行可以从两个互补视角理解：

- 静态视角：代码和指令序列，适合把握整体结构。
- 动态视角：逐条指令造成的状态转移，适合解释指针、递归、函数调用和难以理解的局部行为。

**[必做] 画出求和程序的状态机**

对讲义中的 `1+2+...+100` 指令序列，用三元组 `(PC, r1, r2)` 表示状态。从以下序列继续，画出前两次循环和最后两次循环，直到 `PC=5` 的自循环：

```text
(0, x, x) -> (1, 0, x) -> (2, 0, 0) -> (3, 0, 1) -> ...
```

该题同时是 `1.7` 的实验报告必答题。

**[原则] 程序的微观本质是状态机。** 后续调试时，不要只问“这段代码是什么意思”，还要问“执行这一行前后，哪些状态发生了什么变化”。

## 4. 读懂 NEMU 框架（对应 1.3）

### 4.1 只关注当前路径

NEMU 主要由 monitor、CPU、memory 和 device 构成。PA1 暂时只需关注前三者及 SDB；设备在 PA2 再处理。不要试图一次读完所有源码。

关键目录：

```text
nemu/
├── Kconfig                         # 配置描述
├── include/generated/autoconf.h   # kconfig 生成的 C 宏
├── include/config/auto.conf       # kconfig 生成的 Make 变量
├── scripts/build.mk               # 编译规则
├── src/cpu/cpu-exec.c             # 指令执行主循环
├── src/memory/paddr.c              # pmem 和物理地址访问
├── src/memory/vaddr.c              # 客户虚拟地址访问接口
├── src/isa/$ISA/                   # ISA 相关状态、初始化和执行
├── src/monitor/monitor.c           # monitor 初始化与镜像装载
├── src/monitor/sdb/sdb.c           # SDB 命令
├── src/monitor/sdb/expr.c          # 表达式求值
└── src/monitor/sdb/watchpoint.c    # 监视点池
```

### 4.2 配置与构建

`make menuconfig` 读取 `Kconfig`、保存 `nemu/.config`，并生成供 C 与 Makefile 使用的配置。源码中的 `CONFIG_xxx` 和构建时参与编译的文件都可能受它影响。

用下面的命令只打印完整构建命令而不执行，从实际展开结果反推 `CC`、`CFLAGS`、`$@`、`$<` 和文件列表：

```bash
make -nB
```

**[提示] GDB 阅读框架**

在 `make menuconfig` 中启用：

```text
Build Options
  [*] Enable debug information
```

清理后重新编译。使用断点、单步、打印变量、查看调用栈和 `layout split` 跟踪动态调用路径。RTFSC 不等于盯着静态代码看。

### 4.3 客户程序如何开始执行

1. `init_isa()` 把 ISA 相关的内置客户程序装入 `RESET_VECTOR`。
2. `restart()` 初始化 CPU，令 `cpu.pc` 指向客户程序。`riscv32` 的 0 号寄存器始终为 0。
3. `load_img()` 若收到镜像路径，就用镜像覆盖内置客户程序；否则继续执行内置程序。
4. `sdb_mainloop()` 等待命令，`c` 调用 `cpu_exec((uint64_t)-1)` 持续执行。
5. 客户程序执行 `nemu_trap` 后，NEMU 报告：
   - `HIT GOOD TRAP`：客户程序正确结束。
   - `HIT BAD TRAP`：客户程序以错误状态结束。
   - `ABORT`：模拟器或客户程序意外终止。

`riscv32` 的物理内存从 `0x80000000` 开始；`guest_to_host()` 把客户物理地址映射到宿主数组 `pmem` 的偏移。客户代码访问内存时应使用框架提供的 `vaddr_read()` / `vaddr_write()` 等接口，不要绕过抽象直接操作 `pmem`。

### 4.4 框架阶段任务

**[必做] 首次运行 NEMU**

```bash
cd ics2025/nemu
make run
```

- 确认欢迎信息中的 ISA 是 `riscv32`。
- 根据报错定位并删除 `welcome()` 中要求删除的练习代码，重新编译。
- 在 `(nemu)` 输入 `c`，内置程序应得到 `HIT GOOD TRAP`。

**[必做·仅 x86] 实现寄存器结构体**

只有选择 x86 才需要在 `nemu/src/isa/x86/include/isa-def.h` 中用匿名 `union` 实现 32/16/8 位寄存器的重叠关系，并通过 `reg_test()`；`riscv32` 不做此题。

**[必做] 理解框架代码**

至少能回答：客户程序在哪里装入、PC 在哪里初始化、`c` 如何到达 `exec_once()`、内存通过哪个接口读取，以及 `nemu_trap` 如何改变 NEMU 状态。看不懂某段时用 GDB 跟踪真实路径。

**[必做] 优美地退出**

启动 NEMU 后直接输入 `q`，分析终端错误的原因并修复，使主动退出不再输出错误。不要只屏蔽输出；应理解 NEMU 状态与进程返回值的关系。

## 5. 阶段 1：实现 SDB 基础命令（对应 1.4）

### 5.1 命令规格

| 命令 | 功能 | PA1 要求 |

解析命令前先 RTFM：

```bash
man readline
man strtok
man sscanf
```

注意 `strtok()` 会修改原字符串并维护内部状态；不要在尚未保存剩余参数时随意再次调用。所有命令都要检查缺失参数、非法数字和空表达式，避免把错误输入传给下层。

### 5.2 实现顺序

**[必做] `si [N]`**

- 无参数时执行 1 条，有参数时解析正整数 `N`。
- 调用已有的 `cpu_exec(N)`，不要复制 CPU 执行逻辑。
- 用框架的指令打印功能验证确实只执行了指定条数。

**[必做] `info r`**

- `sdb.c` 只负责分发 `info r`。
- ISA 差异封装在 `nemu/src/isa/$ISA/reg.c` 的 `isa_reg_display()` 中。
- 输出所有通用寄存器和 PC；格式不限，但必须便于人工核对。

**[必做] `x N EXPR`**

- 阶段 1 可先把 `EXPR` 限制为十六进制常量，阶段 2 完成后改为调用 `expr()`。
- 求出起始地址后，每次读取 4 字节并以十六进制显示，共读取 `N` 次。
- 使用客户内存访问接口，不能直接索引 `pmem`。
- `riscv32` 可查看 `0x80000000` 附近，并与内置客户程序字节比较。

**[必读] 这些命令是后续调试基础设施，错误实现会污染所有后续判断。每完成一个命令立刻做正常、边界和错误输入测试。**

阶段 1 最小验收：

```text
si
si 3
info r
x 4 0x80000000
```

确认执行条数、PC 增量、寄存器输出和内存内容相互一致。

## 6. 阶段 2：表达式求值（对应 1.5）

实现位置主要是 `nemu/src/monitor/sdb/expr.c`。采用“正则词法分析 + 递归求值”，先只支持算术表达式。

### 6.1 词法分析

初始 token 集：十进制整数、`+ - * / ( )` 和空白。规则必须处理两层转义：C 字符串转义与正则表达式元字符。

**[必做] 实现算术表达式词法分析**

- 补齐各 token 的正则规则。
- 规则必须从当前 `position` 开始匹配。
- 空白标为 `TK_NOTYPE` 并丢弃。
- 数字 token 同时保存类型和原始字符串；运算符只需保存类型。
- 检查 `tokens[]` 数量和 `Token.str[]` 长度，溢出时明确失败，绝不能越界写入。
- 无规则匹配时返回失败，并报告失败位置。

建议先临时打印 token 序列，覆盖：

```text
1
1+2
1 + 2 * 3
(1 + 2) * 3
((1))
1 + @
```

### 6.2 递归求值

算术表达式 BNF：

```text
<expr> ::= <number>
  | "(" <expr> ")"
  | <expr> "+" <expr>
  | <expr> "-" <expr>
  | <expr> "*" <expr>
  | <expr> "/" <expr>
```

`eval(p, q)` 的处理顺序：

1. `p > q`：非法空表达式。
2. `p == q`：必须是单个数值 token，转换并返回。
3. 整段被一对匹配括号包围：递归求 `eval(p + 1, q - 1)`。
4. 否则找主运算符，递归求左右子表达式，再执行运算。

主运算符必须满足：不在括号内；优先级最低；同优先级时按结合性选择最后结合的运算符。对左结合的二元算术运算，扫描时通常选择最右侧同优先级运算符。

`check_parentheses()` 必须区分：

- 整个表达式由一对匹配括号包围。
- 括号合法，但没有包围整个表达式。
- 括号本身不合法。

所有结果按 `uint32_t` 解释；非法表达式通过 `success` 向上层报告，不要返回一个会被误认为有效结果的值。

**[必做] 实现递归求值与 `p EXPR`**

至少覆盖优先级、结合性、嵌套括号、空白、非法 token、括号不匹配和除零。完成后 `p` 命令调用 `expr()` 并根据 `success` 决定打印结果或错误。

**[选做·编程] 一元负号**

区分二元减法与一元负号，并在寻找主运算符和递归分裂时正确处理，例如 `1 + -1`、`--1`。这个思路会在阶段 3 区分乘法和解引用时复用。

### 6.3 随机差分测试

**[必做] 实现表达式生成器**

在 `nemu/tools/gen-expr/gen-expr.c` 实现 `gen_rand_expr()`：

- 按 BNF 随机生成数、括号表达式或二元表达式。
- 使用 32 位无符号运算，使 C 参考程序与 NEMU 语义一致。
- 随机插入空格。
- 限制递归深度和输出长度，防止栈或 `buf` 溢出。
- 过滤参考程序编译/运行失败及除零用例。

生成测试：

```bash
cd nemu/tools/gen-expr
make
./gen-expr 10000 > input
```

每行格式是：

```text
结果 表达式
```

为 NEMU 增加临时批量测试入口，逐行调用 `expr()` 与参考结果比较；长表达式可能要求扩大 `tokens[]`。测试完成后不要让临时代码破坏正常 monitor 流程。

**[原则] 调试公理与 KISS**

- 机器永远是对的；输出不符合预期，先检查程序和自己的假设。
- 未测试代码永远是错的，尤其是“肯定没问题”的边界路径。
- 从最小功能开始，一次只增加一项并立即测试。先得到简单、可运行、可验证的实现，再处理额外功能。

## 7. 阶段 3：完整表达式与监视点（对应 1.6）

### 7.1 扩展表达式语法

**[必做] 实现完整 BNF**

```text
<expr> ::= <decimal-number>
  | <hexadecimal-number>
  | <reg_name>
  | "(" <expr> ")"
  | <expr> "+" <expr>
  | <expr> "-" <expr>
  | <expr> "*" <expr>
  | <expr> "/" <expr>
  | <expr> "==" <expr>
  | <expr> "!=" <expr>
  | <expr> "&&" <expr>
  | "*" <expr>
```

实现要点：

- 十六进制数以 `0x` 开头。
- 寄存器名以 `$` 开头，通过 `isa_reg_str2val(const char *s, bool *success)` 读取；支持 PC 和本 ISA 的通用寄存器名。
- `==`、`!=`、`&&` 的优先级和结合性与 C 一致，词法规则要把双字符运算符放在可能产生前缀冲突的规则之前。
- 词法分析后，根据 `*` 的前一个 token 判断它是乘法还是一元解引用；表达式开头，或前一个 token 不能作为表达式结尾时，标为 `DEREF`。
- 解引用总是通过客户内存接口读取一个 4 字节值。
- `riscv64` 主线应使用 `uint64_t`；本笔记默认 `riscv32`，使用 `uint32_t` / `word_t`。

回归测试不能只测新功能；原有算术随机测试必须继续全部通过。再手工覆盖：

```text
p 0x10 + 10
p $pc
p $pc == 0x80000000
p 1 != 2 && 3 == 3
p *0x80000000
p *($pc + 4)
```

### 7.2 监视点池

框架在 `nemu/src/monitor/sdb/watchpoint.c` 提供固定池：

```c
static WP wp_pool[NR_WP];
static WP *head = NULL, *free_ = NULL;
```

`head` 管理使用中的监视点，`free_` 管理空闲节点。`WP` 至少还要保存表达式字符串和上一次的值。

**[必做] 实现 `new_wp()` / `free_wp()`**

- `new_wp()` 从 `free_` 摘下节点并加入 `head`；池为空时明确报错或按讲义建议断言。
- `free_wp()` 从 `head` 精确删除目标节点，清理内容后归还 `free_`。
- 正确处理空链表、头节点、中间节点、尾节点、重复/非法释放。
- 用断言维护不变量：节点不能同时出现在两条链表中，活动数加空闲数恒为 `NR_WP`，链表不能成环。

### 7.3 监视点命令与执行检查

**[必做] 实现 `w`、`info w`、`d` 和触发逻辑**

- `w EXPR`：先求初值，成功后申请节点并保存表达式和当前值；失败时不能占用节点。
- `info w`：打印编号、表达式和当前/旧值，格式可参考 GDB。
- `d N`：按编号查找并释放；编号不存在时报告错误，不能破坏链表。
- 在 `trace_and_difftest()` 末尾逐条指令扫描活动监视点。重新求值后若值变化：
  - 输出监视点编号、表达式、旧值和新值。
  - 更新保存值。
  - 设置 `nemu_state.state = NEMU_STOP`，返回 SDB。

监视点每条指令求值会显著降低性能。用 `CONFIG_WATCHPOINT` 包围检查逻辑，在 `nemu/Kconfig` 添加开关，并通过 `make menuconfig` 控制；不需要时关闭。

建议验收序列：

```text
w $pc
info w
si
info w
d 0
info w
```

还应覆盖：创建多个监视点、删除头/中/尾节点、删不存在编号、用完全部节点、表达式不变时不暂停、两个监视点同一步变化，以及删除后再次分配。

**[扩展阅读] 用监视点模拟断点**

```text
w $pc == ADDR
```

当 PC 到达 `ADDR` 时布尔表达式发生变化并暂停。它会每条指令求值，性能远低于真实调试器通过替换指令实现的软件断点。

## 8. Debug 方法

### 8.1 推荐顺序

1. 保持 `-Wall -Werror`，先消除全部编译警告。
2. 对数组边界、指针、链表不变量和表达式成功状态添加 `assert()`。
3. 在 `make menuconfig` 中开启 GDB 调试信息和 Address Sanitizer，清理后重编译。
4. 用 `Log()` / `printf()` 观察 token、递归区间、主运算符和链表变化；输出要换行，避免缓冲区未刷新造成误判。
5. 输出仍不足时，用 GDB 的断点、单步、监视点、调用栈定位最早出现的错误状态。

Address Sanitizer 配置：

```text
Build Options
  [*] Enable debug information
  [*] Enable address sanitizer
```

旧版 `readline` 可能自身泄漏。若 ASan 栈明确指向 `libreadline.so`，该泄漏可以忽略；越界、use-after-free 等其他报告不能忽略。

### 8.2 常见故障

| 现象 | 优先检查 |
| --- | --- |
| 正则初始化断言失败 | C 字符串转义、正则元字符、规则是否合法 |
| 合法表达式匹配失败 | 是否要求从当前 `position` 开始；长规则是否被短前缀规则抢先匹配 |
| 括号表达式结果错误 | 区分“整段被包围”和“括号仅属于子表达式”；括号深度是否归零 |
| `1-2-3` 结合错误 | 同优先级主运算符是否选了正确方向 |
| `*` 表达式报错 | 乘法与 `DEREF` 分类；一元运算符在主运算符扫描中的优先级 |
| `x` 输出不对 | 地址解析、读取宽度、地址步长、客户地址访问接口 |
| 监视点不触发 | 是否在每条指令后检查；旧值是否初始化；是否设置 `NEMU_STOP` |
| 删除监视点后崩溃 | 单链表前驱、头节点删除、节点归还顺序、悬空指针 |
| 随机测试偶发崩溃 | 除零、递归过深、表达式/Token 缓冲区溢出、参考程序编译失败 |

### 8.3 从 failure 回溯 fault

- Fault：错误代码，例如把比较写成赋值。
- Error：执行中首次出现的错误状态。
- Failure：最终可见的崩溃或错误输出。

调试目标不是在 failure 附近乱改，而是借助测试、断言、日志、ASan 和 GDB 找到最早的 error，再回溯产生它的 fault。
